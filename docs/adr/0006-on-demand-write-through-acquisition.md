# ADR 0006：研究数据采用按需采集与伴随沉淀

## 状态

已接受，2026-07-22。

## 背景

当前 MVP 的核心目标是逐类固化高质量研究工作流，而不是预先建设全市场、全时段的数据仓库。持续调度曾经产生大量暂时无法被业务消费的数据，同时个股深研 V3 又只读取既有数据库，导致本地数据缺失或过期时只能输出系统状态，无法在一次研究任务中完成补证。

现有能力包括本地 SQLite 研究库、正式公告与财报脚本、行情及新闻接口、Firecrawl，以及模型/研究 Agent。它们缺少统一的数据需求、缓存判断、执行记录、原始材料和写回契约。

## 决策

1. 默认使用 `refresh_if_stale`：先读本地数据，只有完整性、时效性或权威等级不达标时才采集。
2. 保留 `cache_only` 供测试与复现，保留 `force_refresh` 供排错和关键复核。
3. 所有采集采用 write-through：原始材料、标准化事实、候选证据和数据集状态必须在同一次请求中落库。
4. `last_checked_at` 表示最近检查来源的时间；`available_through` 表示来源实际发布数据覆盖到的日期。两者禁止混用。
5. 确定性连接器负责正式公告、财务、行情和估值；Firecrawl 只承担网页运输与提取；LLM/Agent 负责意图、计划、开放式发现和综合。
6. Agent 输出只能进入 `evidence_candidate`，不能直接覆盖 `normalized_fact`。
7. 同实体、同字段、同口径、同日期的不同数值同时保留；新值标记为 `conflict`，不得覆盖已核验事实。
8. 提供者按数据类型、市场、最低权威等级和优先级路由；主源失败后才尝试经过验证的降级源。
9. 自用 MVP 继续使用 SQLite 和进程内编排，不引入消息队列、微服务或全量定时采集平台。

## 结果

### 正面

- 工作流可以在一次任务中补齐真正需要的数据，并把补证转化为下次可复用资产。
- 网络失败时仍可明确区分新鲜缓存、陈旧缓存和完全缺失。
- 每一个事实都能追溯到采集请求、提供者和原始材料。
- 后续数据源替换只需新增 Provider，不需要重写研究工作流。

### 代价

- 首次研究某个标的的延迟高于纯数据库读取。
- 来源连接器必须实现严格的原始材料和日期口径。
- 数据冲突需要额外的验证或人工复核环节。

## 失败模式与保护

- 主源超时：记录失败执行，按优先级尝试降级源。
- 所有来源失败：不删除旧数据，返回失败和逐源错误。
- 缓存过期：只允许作为历史背景，并保留实际 `available_through`。
- 候选来源权威等级不足：不进入本次高要求采集路由。
- 新旧事实冲突：隔离新事实，并把数据集状态降为 `conflict`。
- 原始材料引用不完整：整批拒绝入库，避免孤立事实。
